# S16 进度偏差诊断：动态经营知识与使用规则

> 本文件是 S16 Skill 的业务知识依据。能力名称、目录名、capability ID 与 node ID 均保持不变。  
> 主要依据：`Digital-Employee-Algorithm-Technical-Spec-2026-07-08.md`。  
> 真实字段映射、公式、阈值、样本门槛、周期可比性和动作资格必须由确定性代码完成；本文件只规定业务解释顺序和因果边界。

## 0. 能力边界

### S14

S14 保持独立的静态经营诊断能力，适合昨日、近 7 天、近 30 天、自然月、推广、活动、评价、历史动作效果和经验沉淀。

S14 在用户明确调用静态复盘时，可以按自身需要读取或消费 S15、S16 的结果；但 S14 不是 S16 的前置依赖，也不是 `S15 → S16 → 具体执行能力` 的必经一级。本次不修改 S14。

### S15

S15 继续名为“销售基准线”，负责完整、可信、可核查的基准数据包：

- 全店和房型最终销售目标；
- 全店和房型小时销售基准；
- 大盘订单和市场份额基准；
- 浏览、一转和二转基准；
- 房型实际成交参考；
- 同一 OTA 商品的历史价格基准；
- 引流价和排名基准；
- 样本、成熟度、时间范围、数据缺口和可比性。

S15 可以说明每条基准自身是否成熟、可比和可用，但不负责当日跨基准归因，不生成调价或推广动作。

### S16

S16 继续名为“进度偏差诊断”。销售进度偏差是入口，随后使用其他基准解释偏差原因。

S16 消费：

1. S15 基准数据包；
2. 当前全店和房型销售事实；
3. 当前大盘、份额、浏览、一转和二转事实；
4. 当前库存、推广、活动、引流价和 OTA 商品价格；
5. 已有动作、观察期和冷却期状态。

S16 输出当日经营判断、原因、动作方向、对象、观察期和资格，但不直接执行动作。具体调价候选和任务交给 S5/S6；推广执行交给推广相关能力。

## 1. 第一原则

任何当日经营判断必须先回答：

> 当前目标入住日期在当前时点，相对历史同类日期的正常销售节奏，是偏快、正常还是偏慢？

禁止先看价格、推广或活动后直接给动作。

销售小时基准匹配优先级：

```text
同季节 + 同节假日 + 同星期几 + 同小时
→ 同季节 + 同节假日 + 同平日/周末 + 同小时
→ 同季节 + 同节假日 + 同小时
→ 同星期几 + 同小时
→ 同平日/周末 + 同小时
```

只有日级数据时，必须使用日级匹配，不得伪造小时浏览、一转、二转、大盘或排名基准。

## 3. 数据门禁

确定性代码必须先检查：

- 数据属于当前酒店和目标入住日期；
- 快照不晚于请求截止时间；
- 不跨酒店、跨平台、跨商品借数；
- 当前事实的新鲜度；
- 当前值与历史值粒度、统计周期和单位一致；
- 来源是否冲突；
- 样本和成熟度是否满足；
- 商品价格是否可比；
- 观察期和冷却期是否结束。

### 预售快照

目标入住日前抓取的预售快照可以展示最后已知已售、库存、房型和快照时间，但不能冒充当前小时进度，也不能形成动作候选。

### 周期不可比

例如：

```text
当前日内累计浏览 != 历史完整日浏览
```

此时可以展示两边事实，但不能计算强弱、比值或动作资格。

### 来源冲突

美团基础经营和流量漏斗可能重复提供浏览和支付订单：

1. 浏览和支付优先采用流量漏斗；
2. 大盘估算采用具有同行均值和同行范围的市场比较指标；
3. 同周期来源不一致时标记冲突；
4. 来源冲突只展示事实，不形成强结论。

### 携程

先按当前 `hotel_id` 和启用渠道自然过滤。普通回复默认不提及没有匹配到的携程数据。用户明确询问且数据主体不一致时，只说明：

> 当前携程数据主体与本酒店不一致，本次未纳入分析。

## 4. 基准成熟度

| 历史沉淀 | 同星期样本 | 使用方式 |
|---|---:|---|
| 1–7 天 | 约 1 个 | 只展示趋势，不判断 |
| 8–29 天 | 约 1–3 个 | 只提示，不生成动作 |
| 30–55 天 | 约 4–7 个 | 可轻判断，只给人工提醒 |
| 56–89 天 | 约 8–12 个 | 可正常判断 |
| 90 天以上 | 约 13 个以上 | 可支持更强判断 |

普通回复只使用业务中文，例如：

> 历史共 21 天，本次选取 3 个同星期几样本。样本较少，目前仅供趋势观察，不作为自动动作依据。

## 5. 经营解释顺序

这是一条 Skill 的解释顺序，不要求实现成单一、臃肿的 Python 总状态机。确定性代码分别给出各轴状态和门禁；Skill 按用户问题选择必要部分并组织解释。

### 5.1 全店销售进度

```text
sales_progress_delta_pp = current_progress_ratio - target_progress_ratio
```

| 偏差 | 状态 |
|---:|---|
| `>= +15pp` | 明显偏快 |
| `+8pp ~ +15pp` | 偏快 |
| `-8pp ~ +8pp` | 正常 |
| `-15pp ~ -8pp` | 偏慢 |
| `-25pp ~ -15pp` | 明显偏慢 |
| `<= -25pp` | 严重偏慢 |

整体正常或偏快时，不优先降价或开推广，但仍要检查房型结构。

### 5.2 房型销售结构

每个房型展示当前已售、总房量、最终目标、当前应售、间数差、偏差、样本和成熟度。

结构类型：

- 多数主要房型普遍偏慢；
- 单个或少数重要房型结构性偏慢；
- 偏快和偏慢房型相互抵消；
- 低房量房型只差一间时优先说明间数，不夸大百分比。

### 5.3 大盘冷暖

无平台直接大盘订单时允许估算：

```text
estimated_market_orders
= own_pay_orders + peer_average_pay_orders × (peer_hotel_count - 1)
```

```text
market_heat_ratio = current_market_orders / baseline_market_orders
```

| 比值 | 状态 |
|---:|---|
| `>= 1.10` | 偏热 |
| `<= 0.90` | 偏冷 |
| 其他 | 正常 |

估算值必须称为“估算大盘订单”。

### 5.4 市场份额

```text
estimated_market_share = own_pay_orders / estimated_market_orders
market_share_delta_pp = current_market_share - baseline_market_share
```

| 变化 | 状态 |
|---:|---|
| `<= -3pp` | 偏弱 |
| `<= -5pp` | 明显偏弱 |

经营组合：

- 大盘冷、份额正常：主要是市场需求不足；
- 大盘冷、份额下降：市场冷且本店竞争力下降；
- 大盘正常或热、份额下降：市场有订单但本店被同行抢单；
- 大盘正常或热、份额正常：继续看流量和转化。

份额下降不能单独触发降价。

### 5.5 浏览

```text
browse_ratio = current_browse_users / baseline_browse_users
```

| 比值 | 状态 |
|---:|---|
| `< 0.80` | 明显不足 |
| `0.80–0.90` | 偏弱 |
| `0.90–1.10` | 正常 |
| `> 1.10` | 较强 |

销售慢且浏览弱，优先检查推广、排名、引流商品库存、主图、视频、标题、标签和活动曝光。浏览弱不等于价格高。

### 5.6 一转

```text
first_conversion = browse_users / exposure_users
```

强判断门槛：

```text
exposure_users >= 300
browse_users >= 30
```

一转弱表示用户看见酒店但没有进入详情页，优先检查列表入口吸引力，不直接降价。

### 5.7 二转

```text
second_conversion = pay_orders / browse_users
conversion_index_vs_market = own_second_conversion / peer_second_conversion
```

强判断门槛：

```text
browse_users >= 50
pay_orders >= 3
```

小体量放宽为浏览至少 30、支付至少 2 时，只允许弱提示。

只有同时满足销售偏慢、浏览不弱、二转低于自身 P25、同行指数低于 0.85 且样本满足时，才能判二转偏弱。

### 5.8 商品价格

只有二转已判弱后才检查价格。

价格高低必须基于同一：

- 酒店；
- 平台；
- `ota_product_id`；
- 商品类型；
- 目标入住日或可比窗口；
- 入住人数、间数和晚数；
- 套餐、早餐、取消、税费和优惠口径；
- 商品自己的连续历史价格。

没有合格商品历史时：

- 展示当前商品价格；
- 标记暂无可比商品历史；
- 不判断高低；
- 不进入调价候选。

PMS 房型价格只显示为“房型实际成交参考”，不能证明 OTA 商品挂牌价偏高。

## 6. 问题和动作

问题类型由代码生成，Skill 翻译，不在普通飞书展示内部代码。每个问题应说明：问题、范围、证据、限制、置信度和下一步。

S16 每次最多给 1 个主要动作候选和 2 个非执行提醒。动作只包含方向、对象、原因、观察期、人工确认要求和下游能力。

### 调价方向

只有商品级价格历史可比且完整证据链成立时，才能交 S5 继续核验。S16 不计算最终执行价，不写任务。

### 推广方向

销售偏慢、浏览不足、成交承接不弱且市场不冷时，可建议交推广能力核验。二转弱时禁止先增加推广。

### 继续观察

以下情况直接继续观察：

- 销售正常；
- 样本不足；
- 周期不可比；
- 来源冲突；
- 当前事实过旧；
- 商品价格不可比；
- 观察期未结束；
- 刚执行过同类动作；
- 关键证据缺失。

## 7. 风控

- 同一日期、同一房型 24 小时内最多 2 次降价；
- 每次降价后至少观察 1.5 小时；
- 接近门店底价或商品历史 P20 时停止降价；
- 不允许全房型一起降价；
- 推广先观察浏览恢复，再观察订单改善；
- 不写“加预算”或“降预算”；
- 观察期未结束不重复同类动作；
- 动作历史未接通时不允许自动执行资格。

## 9. 代码、Skill 和 AI 的分工

### 确定性代码

负责真实字段映射、酒店和日期范围、当前事实、公式、阈值、样本门槛、基准匹配、成熟度、周期可比性、来源冲突、商品价格可比性、问题类型、房型对象、动作资格、优先级、观察期、冷却期和自动执行资格。

这些规则可以拆分成小型、可测试的计算器和门禁，不要求集中在一个总状态机中。

### S16 Skill

负责固定解释顺序、基准的经营含义、指标组合、主要和次要原因、动作或不动作的解释，以及工程状态的业务中文翻译。

### AI 允许

- 组织确定性结果；
- 根据用户问题控制详略；
- 解释房型结构和动作原因；
- 回答现有证据范围内的追问。

### AI 禁止

- 修改数字或阈值；
- 创造不存在的市场、价格和动作证据；
- 样本不足时强判；
- 周期不可比时强判；
- 商品价格不可比时判高低；
- 绕过观察期；
- 声称动作已执行。

## 10. 验收

至少验证：

- 全店和房型两条销售线不混用；
- 小房型不因百分比被夸大；
- 可识别普遍偏慢、结构性偏慢和快慢抵消；
- 当前大盘和份额事实不会因不可比而被删除，但不会强判；
- 一转、二转严格执行样本门槛；
- PMS 成交价不直接证明 OTA 商品价偏高；
- 无商品历史时不输出高低和调价候选；
- 非本酒店渠道数据不进入分析；
- 普通飞书不出现内部英文枚举；
- S16 只输出一次权威正文；
- 观察期未结束时不重复动作；
- S14 可以独立消费 S15/S16，但不是 S16 的前置或动态必经层。
