# S16 进度偏差诊断

> capability_id：`progress_deviation`  
> 当前 service：`s16_progress_deviation`  
> 能力名称、目录名、capability ID 和 node ID 保持不变。  
> 业务知识：[`S16_DYNAMIC_DIAGNOSIS_KNOWLEDGE.md`](./S16_DYNAMIC_DIAGNOSIS_KNOWLEDGE.md)。  
> 美团日内预测规则：[`S16_MEITUAN_DAILY_PROJECTION_AND_ADVISORY_RULES.md`](./S16_MEITUAN_DAILY_PROJECTION_AND_ADVISORY_RULES.md)。  
> 美团活动价格规则：[`MEITUAN_ACTIVITY_NET_PRICE_RULES.md`](./MEITUAN_ACTIVITY_NET_PRICE_RULES.md)。

## 1. 业务职责

S16 仍以销售进度偏差为核心：

1. 判断全店今天整体是否偏慢、正常或偏快；
2. 判断全部房型是否普遍偏慢、结构性偏慢或快慢抵消；
3. 在存在偏差时，使用美团大盘、估算份额、浏览、一转、二转和商品价格参考解释原因；
4. 输出主要原因、次要原因、推广方向和低置信试探涨降价建议；
5. 不直接执行动作。

S16 固定消费 S15 基准数据包，但不依赖 S14。S14 在独立静态诊断场景中可以按自身需要消费 S15/S16。

具体调价候选和任务交给 S5/S6；推广执行交给推广相关能力。

## 2. 代码与 Skill 分工

### 确定性代码必须负责

- 酒店、目标日期和快照范围；
- 当前事实和公式；
- 销售、大盘、份额、浏览、一转、二转分类；
- 阈值和样本门槛；
- 周期可比性和来源冲突；
- 基准成熟度；
- 美团支付订单口径和大盘估算；
- 美团日内历史同小时完成率预测及分量级线性回退；
- 商品价格可比性；
- 美团佣金率归一化；
- 美团商品与活动的精确匹配；
- 底价先扣佣金、全部有效活动系数连续相乘；
- 低置信试探涨降价的对象、方向、幅度上限和观察期；
- 房型对象和问题类型；
- 动作资格、优先级、观察期、冷却期；
- 自动执行资格。

这些能力应拆分成小型、可测试的计算器和门禁，不要求集中为单一大型状态机。

### Skill 负责

- 以销售偏差为第一步；
- 按大盘、份额、浏览、一转、二转、价格的顺序解释；
- 明确大盘、份额、浏览、一转、二转均为美团口径；
- 区分当前事实、预计日终值、预测来源、历史基准和确定结论；
- 根据用户问题选择必要章节，避免无关长文；
- 解释主要和次要原因；
- 说明为什么建议或不建议动作；
- 把工程状态翻译成酒店人员可理解的中文。

## 3. 路由边界

以下请求进入 S16：

- 今天经营怎么样；
- 为什么销售落后；
- 大盘冷不冷；
- 本店有没有丢份额；
- 浏览、一转、二转哪里有问题；
- 今天是否需要调价；
- 今天是否需要开关推广；
- 哪些房型需要处理。

事实快照仍进入 S2，例如：

- 当前出租率多少；
- 今天卖了多少间；
- 还有多少房；
- 给我经营快照；
- 当前 ADR、RevPAR。

基准查询仍进入 S15，例如：

- 查看基准线；
- 历史正常值；
- 样本数量和成熟度；
- P20、中位、P80；
- 完整基准数据包。

## 4. 解释顺序

Skill 按以下业务逻辑组织确定性结果：

```text
销售进度
→ 房型结构
→ 美团大盘估算
→ 美团估算份额
→ 美团浏览趋势
→ 美团一转当前累计率
→ 美团二转当前累计率
→ 美团商品活动后预计收入
→ 原因
→ 推广与试探涨降价建议
→ 动作和边界
```

它是解释顺序，不是要求每次输出所有章节，也不是授权模型自由计算。

## 5. 美团大盘、份额和日内趋势

### 5.1 当前本店美团支付订单

大盘这一组字段统一读取 `meituan_ota_business_metrics`，并以 `PAY_ORDER_CNT` 为主：

```text
本店支付订单 = PAY_ORDER_CNT.metric_value
同行平均订单 = PAY_ORDER_CNT.peer_average
同行排名/酒店数 = PAY_ORDER_CNT.competitor_rank
```

只有某个 `PAY_ORDER_CNT` 字段为空或不可用时，才允许用 `FLOW_PAY_ORDER_CNT` 的同一字段补值，而且 `business_date` 和 `snapshot_time` 必须与该 `PAY_ORDER_CNT` 行完全一致。禁止跨批次、跨日或回退上一天，也不使用 JD01/PMS 订单作为兜底。

### 5.2 美团大盘和份额估算

```text
美团估算大盘订单
= 本店美团支付订单
+ 美团同行平均支付订单 × (美团范围酒店数 - 1)

美团估算份额
= 本店美团支付订单 / 美团估算大盘订单
```

普通回复必须使用“美团大盘估算”和“美团估算份额”，不得省略“美团”和“估算”。当前大盘和当前份额只使用当前时点事实，预计日终投影不改变这两个当前值。

### 5.3 浏览和大盘收盘趋势

S16 优先只读 `meituan_ota_business_metrics_hourly` 的可比历史同小时完成率，把当前累计值换算为预计日终值；该小时表不写回 S15，也不替代 S15 的销售小时基准。

规则固定为：

- 最多读取目标日前最近 60 个自然日；
- 候选历史日复用 S15 最终平台基准的同类日期筛选层级；
- 当前请求小时必须存在精确 `snapshot_hour` 正值，缺小时不插值、不拿前一小时补；
- 单日完成率 = 同小时正值 / 该历史日最后一个正值；至少 1 个有效历史日即可使用，多个取 median；
- 本店支付订单、同行平均订单、浏览分别计算自己的完成率，不共享样本；
- 某一分量没有有效历史完成率时，只允许该分量回退当前日内线性节奏；
- 线性回退仍只在当天已过至少约 35% 时使用；
- 预计日终大盘中的同行酒店数始终使用当前时点 `competitor_rank` 分母，不使用历史圈子大小。

```text
预计本店支付订单 = 当前本店支付订单 / 本店订单历史完成率
预计同行平均订单 = 当前同行平均订单 / 同行平均历史完成率
预计浏览 = 当前浏览 / 浏览历史完成率

预计美团大盘
= 预计本店支付订单
+ 预计同行平均订单 × (当前同行酒店数 - 1)
```

对应历史完成率缺失时，该分量才使用：

```text
线性预计值 = 当前累计值 / 当天已过时间占比
```

输出必须说明预测来源是“历史同小时完成率”还是“线性回退”。预计日终值只能作为趋势参考，不得说成确定收盘结果，也不得冒充美团或 S15 的小时基准。

### 5.4 一转和二转当前趋势

一转、二转是当前累计率，可与历史完整日中位做方向参考，但不能说统计周期完全相同。

- 一转仍要求曝光至少 300、浏览至少 30 才做较强方向判断；
- 二转仍要求浏览至少 50、支付订单至少 3 才做较强方向判断；
- 样本满足时可以说当前累计高于、接近或低于历史中位；
- 二转可以估算按预计浏览量达到历史中位还需多少支付订单；
- 这些趋势不直接产生自动动作。

## 6. 美团活动价格、可比性与试探调价

对每个精确匹配的美团商品，确定性代码按以下顺序计算：

```text
美团商品底价
→ 先扣 commission_rate
→ 匹配该商品当前有效的全部活动
→ 每个活动取一个折扣系数
→ 有几个活动就连续乘几个系数
→ 得到活动后预计酒店收入
```

普通回复必须同时说明：

- 美团商品底价；
- 佣金率及扣佣后底价；
- 匹配活动数量；
- 活动系数连续相乘；
- 活动后预计酒店收入；
- 不含用户券。

没有同一 `ota_product_id` 的合格历史价格时：

- 展示当前商品底价、扣佣后底价和活动后预计酒店收入；
- 说明暂无可比商品历史；
- 不把商品判定为确定的偏高或偏低；
- 不进入自动调价或正式执行候选；
- 允许生成“低置信、只读、试探性”的商品级涨降价建议。

试探建议必须同时满足：

- 仅普通全天房；
- 精确到美团 `ota_product_id`；
- 房型至少 2 间，避免一间房导致百分比夸张；
- 房型销售进度明确偏慢或偏快；
- 已获得扣佣后活动连乘预计收入；
- 已获得 PMS 房型历史成交中位和 P20/P80；
- 降价只在房型偏慢且活动后预计收入高于 PMS 房型成交中位时提出；
- 涨价只在房型偏快、仍有库存且活动后预计收入低于 PMS P80 时提出。

幅度上限：

| 房型进度 | 试探幅度上限 |
|---|---:|
| 偏慢 / 偏快 | 3% |
| 明显偏慢 / 明显偏快 | 5% |
| 严重偏慢 | 8% |

每次最多展示 2 个试探降价和 2 个试探涨价建议，并给出 60–90 分钟观察期。

PMS 房型实际成交价只能作为房型参考，不能直接证明 OTA 商品挂牌价或活动后预计收入偏高。活动后预计酒店收入也不是用户最终到手价或已确认结算价。

S16 只给方向、具体商品、估算幅度、理由、观察期和下游能力。任何写入、审批和执行都必须由 S5/S6 重新读取事实并通过安全门禁。

## 7. 普通飞书输出

固定优先使用六段：

1. 当前结论；
2. 销售进度；
3. 房型结构；
4. 原因判断；
5. 建议动作；
6. 数据限制。

“原因判断”必须明确写出美团大盘估算、美团估算份额、美团浏览、美团一转和美团二转，不能只写“大盘、份额、浏览、一转、二转”。

“建议动作”可以包含：

- 1 个主要经营动作方向；
- 最多 2 个试探降价建议；
- 最多 2 个试探涨价建议；
- 明确“不自动执行，交由 S5/S6 复核”。

根据问题可以省略无关段落，但不能遗漏影响结论的样本、周期、估算口径、价格可比性和未执行边界。

禁止显示：

```text
stable_market_browse_pay_conversion_baseline
stable_lead_price_rank_baseline
M4_same_weekday_daily
WEAK_REFERENCE
period_mismatch
canonical
patch version
metric code
internal status key
```

## 8. AI 禁止

- 修改数字、公式、阈值、佣金率和活动系数；
- 把多个活动改成只取一个活动，或擅自取消活动连乘；
- 在大盘这一组字段中绕过 `PAY_ORDER_CNT` 主值，或使用不同批次/不同业务日的 `FLOW_PAY_ORDER_CNT` 补值；
- 在已有合法历史同小时完成率时改用线性外推；线性只允许作为对应分量没有有效完成率时的回退；
- 把预计日终值说成确定收盘结果或小时基准；
- 省略美团口径，把美团数据写成全渠道数据；
- 创造不存在的市场或价格证据；
- 样本不足时强判一转或二转；
- 商品价格不可比时输出确定的偏高或偏低；
- 把低置信试探调价说成正式调价候选；
- 把活动后预计酒店收入说成用户最终到手价或实际结算价；
- 自行新增确定性代码未生成的动作；
- 绕过观察期或冷却期；
- 声称调价、推广或任务已经执行；
- 对 runtime 权威正文进行二次缩略并丢失边界。
