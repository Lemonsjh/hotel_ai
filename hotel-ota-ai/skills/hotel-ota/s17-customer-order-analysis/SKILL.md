# S17 客户与订单结构分析

## 边界

S17 默认分析酒店和 canonical `room_type_id` 级结构，不做个人评分、联系或定向操作。不同 population 只能并列，禁止相加成“客户总数”。固定 `direct_action_allowed=false`。

经过正式鉴权和 exact `hotel_id` 范围校验后，S17 可以基于 PMS 真实住客姓名统计当前窗口内的已实现到店次数：既支持单个姓名精确查询，也支持用户明确要求时批量展示“客户姓名 + 到店次数”。该能力只用于经营核查，不得附带联系方式、证件信息、订单号、房号，不得自动生成营销、优惠或触达动作。

真实住客主键规则固定为：**`guest_name`（姓名）是住客标识主键**。运行时实际隔离键为 `hotel_id + normalized_guest_name`，禁止跨酒店合并。电话号码/联系人只作为辅助一致性核验，不得替代姓名主键。

内部允许保留统一房型编码用于去重和对账；用户可见正文必须展示真实房型名称。禁止用 `py04`、`py05` 等内部编码代替房型名称。名称缺失时只写“房型名称未映射”，不得回退显示编码。

## 受控入口

```bash
python runtime/hotel_ota_runtime.py customer-analysis \
  --hotel-id <exact_hotel_id> \
  --period-start <YYYY-MM-DD> \
  --period-end <YYYY-MM-DD> \
  --as-of-time <ISO_DATETIME>
```

联系人订单数代理仅在用户主动提供完整联系人且通过权限审计后调用：

```bash
python runtime/hotel_ota_runtime.py customer-analysis \
  --hotel-id <exact_hotel_id> \
  --period-start <YYYY-MM-DD> \
  --period-end <YYYY-MM-DD> \
  --contact-lookup-value <complete_contact>
```

不得回显联系人值。

真实住客频率查询优先从飞书自然语言入口执行，例如：

```text
客户张三到店次数
查询张三的到店频率
张三消费频率
张三到店几次
按照姓名给我统计客户的到店次数
直接展示客户姓名和到店次数
统计所有客户的到店次数
```

单名查询允许回显该姓名的聚合到店次数/窗口内频次；明确批量请求允许回显当前酒店、当前统计窗口内的客户姓名和聚合到店次数。两种结果都不得回显电话号码、联系人原值、HMAC 指纹、证件、订单号或房号。

## 客户姓名与已实现住宿频次

### 数据来源

- 姓名及已实现住宿事实：RS01 `room_fee_daily` / `rs01_room_revenue_daily`。
- 主要字段：`guest_name`、`order_id`、`checkin_time`、`checkout_time`、`business_date`、`charge_subject`、`room_nights`、`snapshot_time`。
- 电话/联系人辅助核验：JD01 `reservation_snapshot` / `jd01_booking_detail` 的 `order_id + contact`。
- 电话在受信边界内转换为酒店域 HMAC，仅用于判断同一姓名关联的联系方式是否一致。

### 姓名总数与频次可计算人数必须分开

窗口内客户姓名总数按 RS01 中有效 `guest_name` 计算：

```text
窗口内有效客户姓名数 = COUNT(DISTINCT normalize(guest_name))
```

姓名标准化只做 NFKC、首尾空白和重复空白折叠；空值及明确无效占位词排除，不做模糊匹配、拼音匹配或相似姓名合并。用户可见口径固定写为“窗口内识别到 N 个有效客户姓名”，并注明“按姓名归并，不代表唯一自然人”。

“有已实现住宿频次证据的姓名数”是另一个指标。只有存在已实现住宿证据的姓名才进入频次统计，禁止把这一子集冒充客户姓名总数。

### 到店次数

```text
到店次数 = COUNT(DISTINCT 已实现住宿订单)
```

**到店频次不按 `charge_subject` 过滤。** `charge_subject` 是收费科目，不是“是否住过”的事实。RS01 记录只要位于统计窗口内、姓名有效且 `room_nights > 0`，即可作为已实现住宿证据；同一订单产生多条收费明细时仍只计 1 次到店。

因此，“房费”“加收全天”或其他收费科目不会改变同一住宿订单的到店次数。收费科目仅用于收入/ADR 的住宿收入分类。

当同一 `guest_name` 关联多个不同联系方式 HMAC 时，不得按电话拆分姓名主键；仍按姓名合并统计，但必须输出 `same_name_multiple_contacts / needs_check`，提示存在同名异人风险。

### 窗口内频次标签

频次只描述当前统计窗口，不推断生命周期首次入住：

| 到店次数 | 展示标签 |
|---:|---|
| 1 | 窗口内1次 |
| 2 | 窗口内2次 |
| 3–4 | 窗口内3–4次 |
| ≥5 | 窗口内5次及以上 |

默认沿用 S17 统计窗口；未指定时为近 30 天，允许窗口范围为 7～365 天。禁止使用“首次/低频/中频/高频”暗示生命周期频次。

## RS01 住宿收入口径

住宿相关收入默认批准科目至少包含：

- `房费`
- `加收全天`

收入金额按批准住宿收费科目求和；实现间夜不能因为同一个住宿事实同时出现多个收费科目而重复累计。

```text
实现间夜 = 同一 business_date + source_platform + order_id + room_no 下，跨批准收费科目去重后的正 room_nights
住宿相关收入 = 批准住宿收费科目金额之和
ADR = 住宿相关收入 / 实现间夜
```

如果同一住宿粒度同时存在“房费”和“加收全天”，金额全部计入住宿相关收入，但间夜只计一次。“加收全天”单独存在且 `room_nights > 0` 时，其住宿事实和金额均可计入。

## JD01 计划到店口径

计划到店结构固定使用：

```text
arrival_time 在窗口内 AND 当前状态 != cancelled
```

取消订单仍单独进入“窗口内取消订单数/取消率”的分子和分母，但不得进入以下结构：

- 计划到店订单数；
- 计划到店房数；
- 计划入住间夜；
- 预订入住时长分布；
- 房型到店结构。

用户可见块名称固定为“计划到店订单”。

## 渠道占比口径

预订渠道占比固定以窗口内**全部订单**为分母。无法识别渠道的订单保留为“未知”桶，不得从分母删除后再计算已识别渠道占比。

例如总订单 584 单，美团 569、携程 8、未知 7，则占比分别约为 97.4%、1.4%、1.2%，分母始终是 584。

## 完整聚合输出与隐私边界

酒店级经营聚合不是个人画像 cohort。以下 S17 聚合分布必须完整展示所有非零桶，不因小样本阈值隐藏，且各桶应能回加到对应分母：

- 预订渠道与客源结构；
- 预订提前期；
- 计划到店入住时长；
- 预订/计划到店房型；
- 实际入住客源与房型；
- 匿名已实现住宿频次分布。

小群体隐私抑制仍保留在联系人代理、平台画像/用户 cohort 等可能接近个人层面的统计。普通 S17 汇总只显示匿名频次聚合；只有用户明确进入“按姓名统计到店次数”能力时，才允许展示姓名 + 聚合次数。

## 飞书正式入口

以下输入必须进入正式 `customer_analysis`，读取当前会话绑定酒店的真实数据库：

- `S17`；
- `完整S17`、`完整 S17`、`详细版S17` 等完整分析请求；
- `客户订单分析`；
- `客户与订单结构分析`；
- `客户/订单聚合分析`；
- `客户<姓名>到店次数/到店频率/消费频率`；
- `<姓名>到店几次/到店次数/到店频率/消费频率`；
- `按姓名统计客户到店次数`、`展示客户姓名和到店次数`、`统计所有客户到店次数` 等明确批量姓名频率请求；
- 主数字菜单 `14`。

只有用户明确输入 `S17 演示` 或同义演示请求时，才允许进入 `customer_analysis_demo`。状态菜单旧编号 `9` 只作为临时兼容别名，实际归一到 `14`。

飞书最终正文直接采用 runtime 的确定性 S17 `summary/send_payload.text`。禁止模型重新计算比例、改写单位、把客源解释为渠道，或追加“顺带说明”“我是怎么路由的”等内部实现说明。

飞书正文禁止出现不必要的数据库或算法字段名，包括 `guest_source`、`customer_source`、`arrival_time`、`contact`、`population` 和 `room_type_id`。单名查询可展示被查询姓名；用户明确要求批量姓名频率统计时，可展示“客户姓名 + 到店次数”。房型结构必须优先读取 `room_type_name`，内部房型编码只保留在结构化证据中，不进入业务正文。

## 独立 population

- `pms_booking_created` / `pms_arrival_cohort` / `pms_booking_contact_proxy`：JD01。
- `realized_stay`：RS01。
- `real_guest_frequency`：RS01 已实现住宿 + JD01 联系方式辅助核验；姓名为主键。
- `extension_reconciliation`：JD04。
- `meituan_scan_order`、`meituan_monthly_background`。
- `provider_order_detail`、`provider_profile_background`、`provider_loss_proxy`。
- `room_mix_background`：JL11，仅用于交叉核查。

S17 不再读取或输出 KF11 当前物理在住 population。

`meituan_scan_order`、`meituan_monthly_background`、`provider_order_detail`、`provider_profile_background`、`room_mix_background` 属于可选增强/交叉核查来源；缺失时保留内部 `source_status`，但不得作为用户可见“数据缺口”污染标准 S17 输出。真正影响核心 S17 指标的缺表、缺字段或缺映射仍必须明确报 `data_gap`，不得借其他酒店、其他 population 或默认值补齐。

## 必须输出的结构

- 订单总览和当前取消结构。
- 订单渠道、客源、预订房数和 canonical 房型矩阵。
- 计划到店订单、计划到店房数、计划入住间夜、入住时长和房型到店结构；取消订单不得进入这些结构。
- 提前预订结构，完整展示全部非零区间。
- 已实现间夜、住宿相关收入和 ADR；“房费 + 加收全天”金额均计入，间夜跨科目去重。
- 窗口内有效客户姓名数，以及其中有已实现住宿频次证据的姓名数。
- 真实住客窗口内到店频次完整聚合分布。
- 当用户明确按姓名批量统计时，展示当前酒店、当前统计窗口内的客户姓名和到店次数。
- 当用户明确查询单个姓名时，展示该姓名的到店次数、窗口内频次标签、首次可见到店和最近可见到店日期。
- 续住核查，独立口径。
- 联系人新旧观察和复购代理，明确不代表实际入住人。
- 平台扫码、画像比例和流失代理背景仅在数据可用且符合隐私阈值时作为增强信息；可选来源缺失不进入标准“数据缺口”。
- 数据窗口、as-of、来源、grain、unit、unmapped 和 suppression 状态。

## 隐私与安全

- `guest_name` 只允许用于 exact hotel scope 内的受控频率统计；单名查询和明确批量姓名频率统计均可回显姓名及聚合到店次数。
- 批量姓名频率结果只允许包含 `guest_name + visit_count`；不得附带手机号、联系人、证件、订单号、房号或其他行级住宿明细。
- 联系人/电话号码只在受信边界以酒店域 HMAC 做辅助一致性核验；原值和 HMAC 均不得进入飞书正文、AI 提示或批量结果。
- 电话号码不得成为真实住客主键，也不得因为号码不同自动拆分同一姓名；出现多个号码时必须提示同名异人核查风险。
- 当 `contact` 源值为脱敏值或字段语义不适用时，联系人辅助核验按安全策略失败关闭，但姓名主键的已实现到店频次仍可在数据完整时计算。
- 禁止电话、联系人、证件、订单号、房号和原始行级订单批量导出；明确的“姓名 + 聚合到店次数”不属于该禁止范围。
- 酒店级匿名经营聚合不套用个人小群体抑制；联系人代理、平台画像/用户 cohort 继续执行小群体、互补可恢复群体和 unknown-denominator 抑制。
- 用户明确要求的姓名到店次数统计按姓名聚合结果直接展示，不套用匿名 cohort 抑制。
- AI 只能解释确定性聚合，不得扩展为兴趣、消费能力、价值评分等营销画像，不得补全隐藏桶或创建动作。
- 生产结果必须经过鉴权、酒店范围校验和飞书输出门禁。
