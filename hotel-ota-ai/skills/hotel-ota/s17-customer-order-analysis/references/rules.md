# S17 客户与订单结构分析规则

## 时间与租户

- 酒店范围只接受服务端解析的 exact `hotel_id`。
- 窗口为酒店本地时区半开区间 `[window_start, min(window_end+1day, as_of))`。
- 所有记录满足 `snapshot_time/collected_at <= as_of_datetime`。
- 每个来源先按批准 dedupe scope 取最新版，再过滤统计窗口和聚合。
- 真实住客到店频次默认沿用 S17 近 30 天窗口；允许 7～365 天。窗口内次数不得宣称为住客生命周期总次数。

## 来源与独立口径

- JD01：创建订单、计划到店、预订客源、渠道、房型、提前期、联系人新旧/复购代理，以及真实住客频次的联系人辅助核验。
- RS01：已实现间夜、住宿相关收入、实际入住客源、实际入住房型、ADR，以及真实住客姓名和已实现到店事实。
- JD04：有效续住核查。
- S17 不再读取或输出 KF11 当前物理在住；物理在住属于其他经营事实能力，不得重新塞回 S17。
- 美团扫码/月度、第三方订单/画像、平台 loss 和 JL11 只作为独立增强或交叉核查背景。来源缺失时不得污染标准 S17 的核心数据缺口，也不得借其他来源补造核心指标。
- 订单、预订房数、计划入住间夜、已实现间夜、住宿收入、真实住客到店次数、续住分别统计，不得互相相加。

## 真实住客到店频次

- 真实住客业务主键固定为 `guest_name`；运行时隔离键为 `hotel_id + normalize(guest_name)`。
- `normalize(guest_name)` 只允许 NFKC、首尾空白清理、连续空白归一和大小写归一；禁止模糊匹配、拼音匹配和相似姓名匹配。
- 电话号码/联系人不是主键，只能作为辅助一致性证据；不得据此把同名记录自动拆分成不同自然人。
- 联系方式关联仅允许通过 exact `hotel_id` 和已批准订单键核验；不得跨酒店关联。
- 已实现到店证据来自 RS01 的 `room_nights > 0`。`charge_subject` 是收入分类，不是住客是否到店的判断条件，因此真实住客到店频次不得按 `charge_subject` 过滤。
- 同一住客姓名下，同一个已实现住宿订单无论产生多少条收费明细，只计 1 次到店。
- 到店时间优先使用 `checkin_time`；缺失时才使用 `business_date` 作为受控降级时间口径。
- 同一姓名关联多个不同联系方式指纹时，仍按姓名主键合并到店次数，但必须提示同名异人核查风险，不得自动拆分或合并为更强的自然人身份结论。
- 窗口内频次标签固定为：1 次、2 次、3–4 次、5 次及以上。不得改写成“首次/低频/中频/高频”等生命周期或价值标签。
- 普通 S17 汇总只展示匿名频次聚合。
- 用户明确要求按姓名统计、列出到店次数、查看回头客/重复到店客户时，展示当前酒店、当前统计窗口内的 `guest_name + visit_count` 聚合结果。
- `客户到店次数分析` 固定解释为“重复到店核查”：除匿名频次聚合外，直接展示窗口内到店 2 次及以上客户的姓名与到店次数。
- `2 次以上人的名字`、`2 次及以上姓名/名单/谁` 等同义请求同样展示 `visit_count >= 2` 的姓名与次数。
- `高频到店客户有哪些`、`展示高频到店客户姓名` 等请求固定解释为当前统计窗口内 `visit_count >= 3` 的姓名与次数；“高频”只作为请求入口别名，确定性正文必须写成“窗口内到店 3 次及以上”，不得扩展为生命周期或客户价值标签。
- 用户明确查询单一姓名时，展示该姓名的窗口内到店次数、窗口内频次标签、首次可见到店日期和最近可见到店日期。
- S17 频次结果的数据合同是姓名与聚合次数；若用户另外询问电话、订单、房号、入住记录等字段，应路由到拥有相应权威字段的查询能力，不得由 S17 频次聚合自行拼接或猜测。这里是能力职责边界，不是“住客隐私”文本禁令。

## 订单、计划到店与实际入住

- `booked_rooms` 固定显示为“预订房数/间预订房”，绝不能显示为“间夜”。
- `guest_source` 固定显示为“预订客源分类”，不能解释成预订渠道。
- `booking_channel` 只能由批准的渠道识别字段/字典派生；未知渠道保留在分母中，不能借 `guest_source` 补齐。
- `created_order_count-current_cancelled_orders` 显示为“当前非取消订单”；状态字段只用于内部核验。
- 计划到店结构按到店时间窗口统计，并排除当前取消订单；必须展示计划到店订单、预订房数、计划入住间夜、入住时长和计划到店房型。
- RS01 住宿相关收入只计批准的住宿收费科目；当前规则包含“房费”和“加收全天”。已实现间夜按同一次住宿跨收费科目去重，0 间夜金额只进入 reconciliation。
- 真实住客到店频次与住宿收入的收费科目规则相互独立：前者只看已实现住宿证据，后者才按批准收费科目核算金额。
- 预订房型、计划到店房型和实际入住房型分别来自各自统计口径，任何一侧为空都不能概括为“全部房型分布为空”。
- 缺统一 `room_type_id` 只计 `unmapped_count`，不得用模糊名称偷偷补齐；公开正文优先显示已经正式映射的 `room_type_name`。

## 完整 S17 输出合同

确定性 S17 正文必须先于 AI 解释完整可读。`完整 S17`、`详细版 S17`、`全部 S17` 与标准 S17 使用同一事实源和同一确定性计算；不得由模型重新算数字或临时删掉已经可用的必需部分。

核心必需结构：

1. 统计窗口、as-of 和核心来源状态。
2. 订单总览：订单数、预订房数、取消/非取消。
3. 预订渠道、预订客源、提前期和完整非零区间。
4. 预订渠道 × 客源 × 房型矩阵；使用房型名称，不向业务正文暴露内部房型编码。
5. 计划到店订单、房数、计划间夜、入住时长和计划到店房型；取消订单不进入计划到店结构。
6. 已实现间夜、住宿相关收入、ADR、实际入住客源和实际入住房型。
7. 有效客户姓名数、有已实现住宿频次证据的姓名数，以及完整匿名到店频次分布。
8. 明确批量姓名频次请求时，追加姓名 + 到店次数；单名查询时追加该姓名的聚合结果。
9. 续住核查。
10. 联系人新旧观察和复购代理；必须明确“预订联系人不代表实际入住人”。
11. 数据质量：统计粒度、单位、房型未映射计数、抑制状态。
12. 平台扫码、平台画像、第三方订单和流失代理等增强背景仅在真实数据可用时展示，并明确不与 PMS 核心口径相加。

可选增强来源不可用时可以省略对应增强段落，但不得因此把核心 S17 标记为不完整或 data gap。

## 禁止混用与解释边界

- JD01 `source_platform` 是来源系统，不是预订渠道；渠道必须走批准的渠道识别规则。
- 联系人不等于实际入住人，联系人代理率不得命名为真实客户复购率。
- 不得通过姓名、联系人、房号或模糊订单号跨不同统计口径自行拼接出没有权威定义的个人画像；需要明细字段时必须读取该字段的权威来源。
- 不得根据订单结构推断“典型电竞酒店”等酒店类型；只允许描述窗口内可见的预订和住宿结构。
- 不得输出“中介渠道占比”；只能输出“中介客源分类占比”和单独的渠道分布。
- AI 只能解释确定性事实，不得改数字、单位、统计口径、映射状态或数据缺口，不得自行扩展为兴趣、消费能力、价值评分等字段，也不得据此创建定向动作。

## 飞书输出

- 正式入口包括 `S17`、`完整 S17`、客户/订单结构请求、单名到店次数请求，以及明确的批量姓名频次请求。
- 飞书最终正文必须直接采用 runtime 的确定性 S17 `summary/send_payload.text`；不得让模型用另一套“安全规则”覆盖 runtime 已经生成的业务结果。
- S17 最终 `send_payload` 使用 `delivery_mode=verbatim`、`model_rewrite_allowed=false`；Agent 必须逐字发送 `send_payload.text`，不能摘要、润色、删减或追加模型自行生成的安全解释。
- 普通 S17 的住客频次默认匿名；`客户到店次数分析` 和明确的姓名频次请求按上文规则展示姓名 + 聚合到店次数。
- **业务字段是否可见由生产鉴权、exact hotel scope 和能力权限决定，不由 `feishu-output-gate` 根据“客户/住客/姓名/名单/订单/房号”等正文关键词猜测。** 通过前置授权且由对应能力真实读取到的数据可以正常出现在飞书业务正文中。
- `feishu-output-gate` 只负责阻断系统级泄密和越过既定执行边界，例如 DSN、token、secret、password、内部身份标识、私有配置/路径、`product_cipher`、源码/原始系统导出及未经允许的运维执行声明。
- 如果某字段不属于 S17 当前数据合同，应说明能力范围或路由到拥有该字段的能力；不得谎称 `raw_order_detail_not_allowed`、`住客隐私` 或其他并未真实发生的安全拦截。
- 固定边界文案应说明：按姓名归并不代表唯一自然人；S17 不生成无权威字段支持的营销画像、不推断酒店类型、不创建定向动作。

## 权限与数据边界

- 所有 S17 查询必须经过生产可信身份、exact `hotel_id` 和角色/能力权限；跨酒店读取仍然 fail closed。
- `guest_name`、订单、入住和房型等酒店业务字段本身不是 final output gate 的禁词；是否返回取决于调用能力是否拥有权威数据以及当前用户是否已通过前置授权。
- 电话不得成为真实住客频次主键；同名不同电话只能产生核查告警，不能自动拆分姓名身份。这是算法主键约束，不是输出隐私规则。
- 平台画像/联系人代理若继续采用小样本抑制，属于对应数据源/指标自己的统计合同；不得把它泛化成“酒店业务数据都不能展示”。
- `direct_action_allowed=false`，S17 分析本身不创建优惠、营销、调价、评论或联系任务。
