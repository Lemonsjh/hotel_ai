# S14 综合运营诊断

## 1. 业务定位

S14 是综合诊断与展示层，不是第二套业务算法，也不是 S2～S17 的批量执行器。

正式 S14 请求只做以下事情：

1. 读取当前已经存在的 versioned deterministic result。
2. 校验酒店范围、目标日期、查询截止时间、版本与状态。
3. 将有效结果归入固定八个诊断模块。
4. 计算问题风险、模块风险、覆盖率、综合风险分和综合健康分。
5. 做数据问题优先、阻断传播、根因聚合、问题去重与排序。
6. 展示七条经营主线、异常房型和已有商品级候选/事实。
7. 原样展示已有 handoff，并说明可继续转交的能力。

**S14 不自动运行、补跑或诊断 S2/S4/S7/S8/S9/S10/S12/S15/S16/S17。** 某个上游 Skill 本次没有已有结果时，不因“没有运行该 Skill”单独生成逐 Skill 报警；对应模块只是不计入有效覆盖。只有已经提供的结果发生范围、时间、版本、状态、证据等问题时，才生成数据质量问题。

S14 不直接读取平行业务表，不自己写 SQL 补数，不重新计算出租率、销售进度、流量转化、价格、ROI、口碑、客户聚合，不调用 OTA/Provider 执行动作。

## 2. 输入资格

一次诊断固定以下请求上下文：

```text
organization_id
hotel_id
target_business_date
as_of_datetime
contract_revision
policy_revision
```

每个已有上游结果至少需要：

```text
capability_id
result_id
result_version
status
hotel_id
target_business_date
as_of_datetime
effective_window
captured_at
source_grain
source_units
deterministic_payload
evidence_refs
quality_flags
contract_revision
policy_revision
```

输入状态统一为：

```text
ok | partial | data_gap | conflict | stale | blocked | not_applicable
```

不得借其他酒店、其他日期、其他平台或不兼容旧版本结果补齐。

## 3. 固定八模块

| 模块 | 权重 | 作用 |
|---|---:|---|
| 经营收益 | 20 | 当前经营事实、销售基准、进度偏差 |
| 流量竞态 | 15 | 市场背景、竞态、曝光和浏览 |
| 转化订单 | 15 | 一转、二转、订单相关结果 |
| 价格库存 | 15 | 库存、可售、价格位置和映射质量 |
| 推广ROI | 10 | 推广事实、计划和已观测效果 |
| 内容入口 | 10 | 活动、权益、引流商品和内容入口 |
| 口碑服务 | 8 | 评分、趋势、主题、未回复和风险 |
| 执行数据质量 | 7 | 身份、时间、freshness、缺失、冲突和阻断 |

只有至少存在一项有效确定性输入的模块才进入覆盖率和综合风险计算。没有结果的模块不按 0 风险参与计算。

## 4. S14 规范指标与算法

| 规范指标 | 算法公式 | 说明 |
|---|---|---|
| 输入资格判定 | 输入有效 = 酒店范围一致 AND 目标日期一致 AND 数据时间未超过查询截止时间 AND 结果版本兼容 AND 数据状态可用 | 校验失败的已有结果不能进入经营评分，应转为数据缺口、冲突、过期或阻断问题。S14 不为补齐输入自动运行其他 Skill。 |
| 诊断模块归类 | 诊断模块 = 根据已有上游结果所属业务方向，归入经营收益、流量竞态、转化订单、价格库存、推广ROI、内容入口、口碑服务、执行数据质量八个模块之一 | S14只对已有结果归类，不重算业务指标。 |
| 严重度分值 | 致命=100；高=75；中=50；低=25；提示=0 | 统一各模块问题严重程度。 |
| 问题风险分 | 问题风险分 = 严重度分值 × 问题置信度 | 置信度为0～1。 |
| 模块风险分 | 模块风险分 = MAX(本模块内未被上游问题阻断的问题风险分) | 每模块取最高有效风险，避免严重问题被平均。 |
| 有效模块判定 | 模块有效 = 至少存在一项有效确定性输入 AND 不存在导致整个模块失效的酒店范围、时间或版本错误 | 只有有效模块权重进入覆盖率和综合风险。 |
| 数据覆盖率 | 数据覆盖率 = 有效模块权重之和 ÷ 100 | 八模块权重合计100。 |
| 综合风险分 | 综合风险分 = Σ(有效模块权重 × 模块风险分) ÷ 有效模块权重之和 | 缺失模块不按0风险参与。 |
| 健康分计算资格 | 健康分可计算 = 数据覆盖率 ≥ 80% | 低于80%时健康分显示无法计算，但已有问题仍展示。 |
| 综合健康分 | 综合健康分 = 100 − 综合风险分 | 只用于人工查看和经营排序。 |
| 数据问题优先 | 若已有输入存在数据缺失、冲突、过期或范围错误，则先生成数据质量问题，再判断其依赖的经营结论 | 数据条件不成立时不得强行输出经营异常。 |
| 阻断传播 | 下游问题状态 = 受上游问题影响；依赖数据不可用时，下游问题不参与模块风险计算 | 例如基线不可用时只标记进度暂不可判断。 |
| 根因聚合 | 根因组 = 根因相同或证据来源相同的问题集合 | 优先展示根问题，避免重复报警。 |
| 问题去重 | 问题唯一标识 = 酒店 + 目标日期 + 所属模块 + 问题类型 + 作用范围 + 证据摘要 | 同一证据重复运行不重复生成相同问题。 |
| 问题排序 | 排序优先级 = 严重程度 → 问题状态 → 所属模块 → 问题类型 → 问题编号 | 同等严重度优先数据冲突、数据缺口、数据过期、经营异常、观察项、正常项。 |
| 第一层经营透视 | 主线结果 = 上游已计算的实际值、基准值、差距值和当前状态 | 固定展示销售进度、大盘订单、市场份额、浏览、一转、二转、价格；S14不重新计算。 |
| 第二层房型透视 | 异常房型集合 = 达到异常条件或存在数据冲突的房型 | 只展示真正异常房型，不把酒店整体异常平均分摊到房型。 |
| 第三层商品透视 | 商品候选集合 = S5或S6已经生成并通过规则校验的商品级候选 | S14只展示已有候选，不自行生成涨价或降价方案。 |
| 结果交接 | 价格问题→S5/S6；推广问题→S8；评论问题→S13 | S14只传递已有问题和结果，不负责审批或执行。 |
| 直接执行资格 | 是否允许直接执行 = 否 | 风险分、健康分和问题排序均不能直接触发经营动作。 |
| AI解释资格 | AI可用 = 确定性诊断、风险评分和排序全部完成后 | AI只能解释已有诊断，不能新增问题、调整严重度、修改评分或产生经营动作。 |

## 5. 风险与健康分规则

严重度映射：

```text
critical = 100
high = 75
medium = 50
low = 25
info = 0
```

问题风险：

```text
item_risk = severity_points × confidence
```

模块风险：

```text
module_risk = MAX(unblocked item_risk)
```

覆盖率：

```text
coverage_score = SUM(observed_module_weight) / 100
```

综合风险：

```text
observed_risk_score = SUM(module_weight × module_risk) / SUM(observed_module_weight)
```

综合健康：

```text
if coverage_score < 0.80:
    observed_health_score = not_computable
else:
    observed_health_score = 100 - observed_risk_score
```

健康分只用于展示，绝不能直接触发价格、推广、评论或其他执行动作。

## 6. 数据问题、阻断、根因与去重

范围错误、未来数据、版本冲突、数据过期、canonical 映射缺失、单位冲突等已有输入问题优先形成 `execution_data_quality` item。

依赖该证据的下游结论保留但标记 `blocked_by=<upstream_item_id>`，且不参与模块风险计算。

多个问题共享同一根因或证据来源时归入同一 root-cause cluster。问题唯一标识由酒店、目标日、module、issue code、scope 和 evidence hash 稳定生成，同一证据重跑不重复产生问题。

排序固定为：

```text
severity -> status -> module -> issue_code -> item_id
```

## 7. 三层经营透视

### 第一层：七条经营主线

固定展示：

```text
销售进度
大盘订单
市场份额
浏览
一转
二转
价格
```

S14只展示已有上游结果中的 actual、baseline、delta/gap、maturity、effective_window 和 status，不自行补算。

### 第二层：异常房型

只展示达到异常条件或存在数据冲突的 canonical room type。正常房型不展示，也不把酒店整体异常平均分摊到每个房型。

### 第三层：商品级候选/事实

只展示已经由 S5/S6 生成并通过规则校验的 exact 商品级候选或当前商品事实。S14不得根据综合风险或健康分自行产生调价候选。

## 8. 结果交接

S14只能展示已有受控 handoff：

```text
价格/收益 -> S5/S6
推广 -> S8
评论 -> S13
```

S14自身不创建任务、不申请确认、不审批、不写任务表、不调用 OTA/Provider。

## 9. AI解释边界

AI只能在确定性诊断、风险评分和排序完成后，对已经存在的 item、证据、根因、核查方向和 handoff 做易读解释。

AI禁止：

- 新增问题；
- 修改严重度；
- 修改问题排序；
- 修改风险分或健康分；
- 解除冲突或阻断；
- 生成新的价格、预算、推广计划或评论动作；
- 申请审批或直接执行。

AI失败时仍应输出确定性 S14 结果。

## 10. 飞书输出

飞书正式输出按以下顺序展示：

1. 目标营业日、数据截止时间、状态；
2. 数据覆盖率、综合风险分、综合健康分；
3. 第一层七条经营主线；
4. 第二层异常房型；
5. 第三层已有商品候选/事实；
6. 优先问题；
7. S14规范指标、公式、当前结果和说明；
8. 已有 handoff 与执行边界。

不得显示原始 SQL、模型参数、客户/评论原始行、物理 ID、Secret 或服务器内部路径。
