# S11 推广建议与控制

## 核心定位

S11 包含两个明确分离的子能力：

1. **推广建议书**：读取同酒店、同渠道、同时间窗口的 S8/S10/S15/S16 正式确定性证据，生成确定性的 `PromotionPlan`；S9 仅作流量参考。建议路径不写任务、不改渠道。
2. **现有推广计划控制**：只允许对已存在的美团推广实例执行“暂停”或“恢复”。执行入口本身不直接操作美团页面/API，而是将经过唯一 `launch_id` 校验的控制任务写入 `ota_promotion_control_task`，初始状态固定为 `pending`，由后续执行器消费。

> S8 提供推广计划/投放事实，也是执行前 `launch_id` 唯一映射的事实源。
>
> S9 仅作为 advisory/reference evidence，用于补充理解曝光、意向和支付漏斗。
>
> S15 是正式经营证据之一，提供销售目标、小时销售基准、历史样本和成熟度。

## 建议输入

### 正式确定性输入

- S8：美团推广通计划/投放单元及推广表现事实。
- S10：推广效果、观测 ROAS、CPA、推广状态等确定性结果。
- S15：全店/房型销售目标、小时销售基准、历史样本与成熟度。
- S16：销售进度及偏差事实。
- 用户当前意图：开启 / 恢复 / 维持 / 观察 / 暂停 / 关闭，或预算/出价建议。

### 参考输入

- S9：美团流量漏斗和转化率事实，仅作为辅助流量参考，不单独决定推广动作。

所有输入必须属于同一 `hotel_id`、同一目标日期/计算时点；推广相关输入必须属于美团渠道。S8/S10/S15/S16 的缺失必须作为正式证据缺口暴露，不能用演示、样例或推测值补齐。S9 缺失只降低流量参考完整度。

生产飞书进入建议路径时，路由应自动按当前酒店、目标日期和 as-of 查询 S15/S16；调用方不需要手工先跑 S15/S16。

### 推广实例快照口径

S11 不使用“全酒店只有一个最新 `snapshot_time`”来筛掉其他推广实例。

对 `meituan_ota_promotion_performance_30d`：

- 必须按当前 `hotel_id` 精确过滤；
- 以 `launch_id` 为推广实例键；
- 每个 `launch_id` 独立选择自己的最新 `snapshot_time`；
- 如有可信 `as_of_time`，每个 `launch_id` 都只能选择不晚于该时间的最新记录；
- 因此一个计划最新记录为 17:06、另一个计划最新记录为 09:46 时，两条都必须进入 S11，而不能只保留 17:06 快照中的计划；
- 每个计划的建议中必须保留自己的 `source_snapshot_time`，不得用全店最大快照时间伪装成所有计划同一时刻刷新。

S8 自身的展示专用全局最新快照合同可以保持不变；上述 `latest_per_launch` 是 S11 建议和推广控制的专用读取口径。

## 建议输出

`PromotionPlan` 至少包含：

- 组合级经营结论；
- `per_plan_recommendations`：按唯一 `launch_id` 输出一条计划级建议；
- 每条计划级建议至少包含 `plan_id`、`launch_id`、当前推广状态、计划自己的最新快照时间、ROAS、CPA、建议动作和原因；
- 建议时间窗；
- 预算与出价；没有明确输入时必须为 `manual_input_required`；
- 活动冲突检查状态；
- 观察指标；
- 停止条件；
- 风险提示；
- 人工操作清单；
- S8/S10/S15/S16 正式来源对齐状态；
- S9 独立的 reference source 状态。

### 分计划建议规则

S11 必须逐 `launch_id` 形成建议，不能只展示不同计划指标后给一个笼统组合动作。

当前确定性规则：

1. 正式证据 S8/S10/S15/S16 任一缺失时，该计划只输出 `观察`，不得猜暂停或恢复。
2. 当前状态无法确认时只输出 `观察`。
3. 对**投放中**计划：
   - S10 观测 `ROAS <= 1`：建议 `暂停`；
   - 当 S16 销售进度已经超前，若另一个同时投放的计划同时满足“ROAS 更高且 CPA 更低”，则当前被严格支配的计划建议 `暂停`；
   - 其他情况建议 `维持`，不因销售超前自动把所有推广都暂停。
4. 对**已暂停**计划：
   - 只有 S16 销售进度落后，且该计划历史观测 `ROAS > 1` 时，才建议 `恢复`；
   - 否则继续 `观察`，明确“暂不建议恢复”。
5. 已结束/已关闭计划不能因为历史绩效好而直接建议 `恢复`。
6. 用户询问“是否应该暂停某计划”时，“暂停”只是用户待评估动作，不能直接变成系统推荐；系统必须按上述证据重新计算。

分计划建议仍然只是只读建议，不创建控制任务。只有用户后续发出明确肯定的暂停/恢复执行命令，才进入任务写入路径。

## 暂停 / 恢复执行合同

执行功能只支持：

- `pause`：暂停一个**现有**美团推广实例。
- `recover`：恢复一个**现有**美团推广实例。

除此之外的执行动作一律不支持。尤其不支持通过本执行入口创建推广计划、关闭/删除计划、调整预算、调整出价或修改其他推广配置。

### launch_id 必须先唯一解析

写任务前必须先查询 `meituan_ota_promotion_performance_30d`，并按当前酒店的 `latest_per_launch` 口径取得推广实例集合，然后满足：

1. 查询范围必须绑定当前已鉴权的 `hotel_id`。
2. `platform` 固定为 `meituan`。
3. 每个 `launch_id` 独立取自己的最新合法快照，不能因另一计划刷新更晚而把它过滤掉。
4. 任务定位键必须使用来源表中的真实 `launch_id`，不得用 `plan_id`、`plan_name`、`launch_name` 或 `promotion_name` 代替。
5. 用户给出推广名称或 `plan_id` 时，它们只能作为查找线索；必须映射到唯一 `launch_id` 后才能写任务。
6. 同名或同一查找标识对应多个不同 `launch_id` 时必须返回 `clarification_required` 并列出候选，不得猜测或写任务。
7. 用户直接给出 `launch_id` 时，也必须验证该 ID 确实存在于当前 `hotel_id` 的 `latest_per_launch` 美团推广实例集合，不能信任裸 ID 直接写任务。
8. 来源没有 `launch_id`、来源不可用或没有匹配项时，必须 fail closed；不得把名称、`plan_id` 或其他字段直接当作任务定位键兜底。

### 任务表写入规则

目标表：`ota_promotion_control_task`。

新任务必须严格写入：

- `hotel_id`：当前已鉴权酒店 ID。
- `platform`：固定 `meituan`。
- `launch_id`：从 `meituan_ota_promotion_performance_30d` 唯一解析并验证的推广实例 ID。
- `action`：只能是 `pause` 或 `recover`。
- `status`：固定 `pending`。
- `error_message`：新任务为空。
- `created_at`：任务创建时间。
- `executed_at`：新任务为空。

任务创建成功只代表“控制任务已进入待执行队列”，不得表述为“美团已暂停/已恢复”。只有后续执行器将任务状态更新为 `success` 并完成渠道回查后，才能声明渠道动作成功。

### 权限边界

生产飞书的暂停/恢复任务写入必须通过可信身份和酒店租户绑定，并要求当前角色拥有 `approve_live_action`。当前权限语义下 owner/admin 可以提交该控制任务；普通建议权限不能转换成执行权限。

## 意图规则

- “给我推广建议 / 是否应该暂停某计划” => 只生成建议书，并按计划输出证据计算后的建议，不写任务。
- 明确命令“暂停推广 <launch_id/plan_id/名称>” => 先映射唯一 `launch_id`，通过权限后写 `pause + pending` 任务。
- 明确命令“恢复推广 <launch_id/plan_id/名称>” => 先映射唯一 `launch_id`，通过权限后写 `recover + pending` 任务。
- 同名/多候选 => `clarification_required`，列出各自 `launch_id`，不写任务。
- “把预算改为 X / 调整出价为 X” => 仍只记录为建议，不执行。

## 证据使用边界

- S10 是推广效果、成本效率和推广状态的正式证据。
- S15 是经营基准正式证据。
- S16 是当前销售进度与偏差的正式经营证据。
- S9 只解释流量漏斗背景。
- S15 与 S16 不一致时同时保留，不互相覆盖。
- 建议证据不能绕过执行入口的 `hotel_id + meituan + unique launch_id + allowed action` 校验。

## 硬边界

- 建议路径仍不得制造任务 ID、派发状态、执行状态或渠道成功状态。
- 执行路径仅允许写 `ota_promotion_control_task` 的 `pause/recover` 待执行任务，不直接写美团渠道。
- 执行路径不得仅按推广名称操作。
- 执行路径不得把新任务状态写成 `processing/success/failed/cancelled`；初始状态只能是 `pending`。
- 旧命令名 `promotion-execute` 继续作为建议兼容入口；只有明确的暂停/恢复执行命令才能进入推广控制任务路径。
