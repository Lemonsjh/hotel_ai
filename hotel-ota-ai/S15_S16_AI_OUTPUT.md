本文件约束生产飞书中的 S15、S16。唯一业务算法依据是 `Digital-Employee-Algorithm-Technical-Spec-2026-07-08.md`；不再使用 `hotel-ota-s1-s17-real-field-algorithm-spec.md` 解释这两个能力。

runtime 生成的数值、房型集合、基准状态、成熟度、数据缺口和动作资格是唯一事实源。算法文档字段名只表示业务语义，实际取数必须映射到真实数据库字段和真实粒度，不能机械按字段名匹配。

## 2. S15 职责

S15 只负责生成完整的历史销售基准数据包，包括：

- 全店与房型历史销售目标和销售进度基准；
- 小时节点基准及历史采集覆盖情况；
- 大盘、份额、浏览、一转、二转、房型价格、引流价和排名等历史参考；
- 样本数量、成熟度、置信度、匹配层级和周期可比性；
- 缺失日期、缺失小时、不可比周期、查询错误和其他数据缺口。

S15 不消费当前动态经营事实，不负责当日经营归因，不生成调价、推广或其他动作候选，也不创建任务或执行动作。

S15 优先读取控制面 SQLite `baselines` 中按 `hotel_id + target_business_date + baseline_package_version` 隔离的物化基准。有效缓存可以按日复用；缓存缺失、损坏、版本变化、历史截止日变化或显式强制重建时才重新计算。不得使用散落 JSON 作为生产基准事实源。

## 3. S15 完整基准矩阵

每次 S15 必须完整展示以下历史基准，不得因某一条不可用而省略整段：

1. **全店最终销售目标基准**：历史同类日最终间夜目标、收入参考、样本和匹配层级；
2. **房型最终销售目标基准**：全部 canonical 房型逐一展示历史最终间夜目标；
3. **全店小时销售进度基准**：容量线、最终目标完成线、关键检查点、样本和成熟度；
4. **房型小时销售进度基准**：全部 canonical 房型逐一展示历史同时点应售基准和覆盖情况；
5. **大盘订单基准**：历史本店订单、同行平均、同行酒店数、估算大盘和热度参考；
6. **本店市场份额基准**：历史估算份额、样本和周期可比性；
7. **浏览基准**：美团日级历史同类日中位、样本和成熟度；
8. **一转基准**：曝光→浏览的历史中位、样本门槛和状态；
9. **二转基准**：浏览→支付的历史自身基准，以及滚动 30 日同行横向参考；
10. **房型历史价格基准**：全部 canonical 房型的加权平均、P20、中位、P80，以及可比商品历史；
11. **引流价及排名基准**：日级历史本店引流价、同行均价、排名和样本；
12. **携程相关基准**：当前酒店身份、canonical 房型映射和历史数据范围通过时展示；不通过时明确整组禁用及原因。

最后还必须展示：基准健康、查询错误、短历史、缺失小时、不可用项、样本和可比性。S15 不在该矩阵中加入当前值、当前归因或动作判断。

## 4. S16 当前销售事实

S16 当前目标入住日的房型事实使用 `pms_room_type_forecast` 中目标日期、请求时点之前最新的完整房型批次：

```text
target stay date = stay_date
collection cutoff = snapshot_time <= as_of_datetime
canonical room = room_type_id
committed sold = MAX(total_rooms - available_rooms + overbooking_rooms, 0)
```

必须按同一合法完整批次读取全部 canonical 房型；批次不完整、业务日期不符或快照晚于请求时点时降级，不得拼接不同批次补齐。

`jd01_booking_detail`、`jd04_inhouse_extension`、`kf11_room_status_snapshot` 不属于 S15/S16 当前房型进度口径，但 S2、S5、S17 等其他能力仍可按各自明确规则使用，不能从项目中删除。

`snapshot_time` 是采集时间，不是营业日期。采集暂停时，最新合法真实快照仍可用于事实展示和趋势判断：

- 必须显示快照年龄；
- 超过时效阈值时标记 `stale_but_usable`；
- 禁止基于陈旧事实生成调价、推广等动作候选；
- 不能把陈旧但真实的数据改称“字段缺失”；
- 也不能拿未来快照补当前事实。

`occupied_rooms` 是物理在住背景，不替代承诺已售。房量、间夜和订单数不得互相按 1:1 转换。

## 5. 小时历史

历史小时销售曲线只来自 `pms_room_type_hourly_status`：

- `snapshot_hour` 是业务检查点；
- `snapshot_time` 只负责版本和新鲜度；
- 同一酒店、入住日、小时只使用最新合法完整 canonical 房型批次；
- 缺小时不插值、不补零、不拿前一小时向后填充；
- 采集刚启动或此前未全天运行造成的短历史，标记为采集覆盖暂时不足，不算字段缺失；
- 关键检查点至少展示 09/12/14/16/18/20/22 点和当前小时；没有真实样本时明确显示缺口。

本节“小时历史”指 S15/S16 的**销售进度小时基准**。`meituan_ota_business_metrics_hourly` 不进入 S15 小时基准，也不替代 `pms_room_type_hourly_status`；它只允许在 S16 中作为美团收盘预测的完成率因子使用，规则见第 7、8 节。

## 6. 最终目标与历史价格

- 全店最终目标使用 `jy01_hotel_statistics_daily` 中 exact `总营业指标/总营业指标`；
- 房型最终目标使用 canonical `jl01_room_type_performance_daily`；
- 房型价格使用 `rs01_room_revenue_daily` 的正常房费记录，按间夜加权；
- JY01 的渠道、客源、房型等纵向维度不得相加冒充酒店总计；
- 房型日终查询失败时必须显示真实查询错误，不能静默退化成全店分摊。

上述历史结果进入 S15 基准数据包；S16 只消费已生成的基准，不在当前诊断中自行改写基准口径。

## 7. 美团日级平台基准与 S16 小时完成率

`meituan_ota_business_metrics` 每个 `business_date + metric_code` 每日一份，因此 S15 的浏览、一转、二转、同行订单、引流价和排名仍只建立**日级基准**，禁止把该日级表生成小时平台基准。

口径：

```text
曝光 UV = FLOW_EXPOSURE_UV
浏览 UV = FLOW_INTENTION_UV
支付订单 = FLOW_PAY_ORDER_CNT
一转 = FLOW_INTENTION_UV / FLOW_EXPOSURE_UV
二转 = FLOW_PAY_ORDER_CNT / FLOW_INTENTION_UV
```

`PAY_ORDER_CNT` 是市场比较行，通常承载 `peer_average` 与 `competitor_rank`；漏斗支付订单仍使用 `FLOW_PAY_ORDER_CNT`。两条指标不能混成一条。

S15 继续使用上述日级事实形成历史参考，不改其基准结构。S16 可以额外只读 `meituan_ota_business_metrics_hourly`，但该表仅用于把“当前累计值”换算为“预计日终值”，不得写回 S15 基准，也不得改变一转/二转的日级历史基准定义。

S16 小时完成率规则：

- 最多读取目标日前最近 60 个自然日，不查询目标日及更早范围；
- 候选历史日必须来自新小时表自身实际可用日期，并读取同一 `calendar_days` 日期标签，复用 S15 最终平台基准实际使用的 `s15_s16_spec_alignment_patch.select_platform_dates` 同类日期筛选层级；
- 每个指标/字段独立判断有效历史日：必须同时存在**当前请求小时的精确 `snapshot_hour` 正值**和该历史日**最后一个正值**；缺当前小时不插值、不拿前一小时补；
- 单日完成率 = `value_at_same_hour / final_positive_value`；至少 1 个筛选后的有效历史日即可使用；多个有效日取 median；
- `PAY_ORDER_CNT.metric_value`、`PAY_ORDER_CNT.peer_average`、`INTENTION_UV.metric_value` 分别计算各自完成率，不共享、不强行对齐样本；
- 某一个分量没有有效完成率时，仅该分量回退现有日内线性节奏，其他已有历史完成率的分量继续使用历史；
- `competitor_rank` 只用于当前时点竞争圈家数，历史小时表中的排名/圈子大小不得替代当前分母；
- 当前 `EXPOSE_PV_CNT.metric_value` 不具备可用小时值时，不据此新增或改写一转小时预测。

## 8. 大盘和份额估算

当平台不直接提供竞争圈总订单时：

```text
estimated_market_orders
= own_pay_orders
+ peer_average_pay_orders × (peer_hotel_count - 1)

estimated_market_share
= own_pay_orders / estimated_market_orders
```

`peer_hotel_count` 使用**当前时点** `competitor_rank` 的分母，例如当前 `3/20` 使用 20。输出必须始终带“估算”，不得伪装为平台直接提供的大盘或份额。

S16 的当前大盘和当前份额仍按上式计算，不因收盘预测而改变。预计日终大盘只替换收盘投影因子：

```text
projected_market_orders
= projected_own_pay_orders
+ projected_peer_average_pay_orders × (current_peer_hotel_count - 1)
```

其中本店支付订单和同行平均订单分别按第 7 节自己的历史完成率投影；对应完成率缺失时各自单独回退线性节奏。历史 `competitor_rank` 不参与预计日终大盘的家数计算。

S15 保存可比历史估算参考；S16 使用当前估算大盘和份额进行经营解释，并把预计日终大盘仅作为趋势参考。

## 9. 二转同行背景

`meituan_ota_flow_conversion_30d` 的一行是一个滚动 30 日窗口：

- 可以作为当前本店与同行二转的横向参考；
- 不能拆成 30 个日样本；
- 不能用于计算同星期日级 P25；
- 持续沉淀多个窗口后才能形成滚动趋势或独立月级参考。

## 10. 商品价格口径

当前价格必须通过 exact `hotel_id + source_product_id + AUTO active mapping + canonical room_type_id` 匹配。

同一房型必须分开：

```text
普通全天房
超级团购
钟点房
```

- 普通全天房优先用于与 PMS 历史成交价比较；
- 只有超级团购时仅作参考，不进入调价候选；
- 钟点房只展示，不参与全天房价格判断；
- 不按房型名称猜商品；
- 不把一个房型的多个商品合并成一个虚假当前价；
- S16 只读调价建议对用户只展示当前和建议后的**预估到手价**；美团挂牌/底价继续保留为内部候选与下游动作参数，不在权威正文展示；
- 建议后的预估到手价在佣金、活动连乘和会员预期折扣因子不变的展示假设下，按 `suggested_raw_price / current_raw_price` 比例从当前预估到手价推算。

S15 提供房型与可比商品的历史价格参考；S16 负责当前价格与可比历史的可比性判断和只读解释，不直接生成或执行调价任务。

## 11. 携程边界

携程数据只有同时满足以下条件才进入本酒店 S15 历史基准或 S16 当前诊断：

```text
hotel identity 一致
canonical room mapping 完整
业务日期和数据范围可用
```

当前数据属于其他酒店或房型映射为空时，携程整组禁用，不参与经营归因、价格比较、大盘估算、份额估算或动作判断。

## 12. S16 职责

S16 消费 S15 基准数据包和当前事实，负责：

1. 判断全店销售进度是偏慢、正常还是偏快；
2. 判断全部 canonical 房型中哪些结构性偏慢或偏快；
3. 判断全店普遍滞后、单房型结构滞后，或房型快慢抵消；
4. 解释当前估算大盘、估算份额、浏览、一转、二转和价格可比性；
5. 给出主要原因、次要原因、数据限制、只读建议和下游能力边界；
6. 展示最新事实批次年龄、小时基准成熟度和数据边界。

每个异常房型必须保留：

```text
房型名
已售 / 总房
同时点应售
间数差
相对同时点基准的具体 pp 偏差
偏快或偏慢状态
```

低房量房型还必须同时说明间数，避免只用百分比夸大影响。已有具体 pp 偏差时，不得只输出“偏快”“偏慢”等标签而省略 pp 数值。

S16 必须完整展示所有异常房型，不能只给一句 `data_gap`；只有确实不存在任何合法事实批次时才返回不可判断。陈旧但合法的真实批次应降级展示并禁止动作。

S16 不直接执行调价、推广、审批或任务写入。具体收益候选由 S5 复核，执行与任务闭环由 S6 或对应推广能力处理。S14 可以独立消费 S15/S16，但不是 S16 的前置依赖。
